# Delivery Standards

**版本：** 1.0

**定位：** 定义所有 Agent 交付说明的统一结构与内容边界，是 `specs/Task_Specification.md` 中 Deliverable 字段的执行细则；PM 据此在 30 秒内完成验收核对。

**适用范围：** Product、UI、Frontend、Backend、Mobile、QA 六个 Agent 的全部 Task 交付。PRD 作为独立对象遵循 `specs/Product_Requirement_Specification.md`，本文件不重复定义。

---

# 1. 核心原则

1. 交付说明 = 结论摘要 + 证据指针：只回答「做了什么、结果如何、如何复核」；完整资产留在 `workspace/`，用链接引用，不复制。
2. 固定模板，按字段填空：没有的内容写「无」，不允许空泛表述。
3. 限长：正文不超过一页 A4；叙述性文字合计不超过 300 字；条目一条一行。
4. 不记录过程：不写工作日志、讨论过程、已完成历史、执行细节。
5. Git 已保存的实现细节不重复写入（继承 BASIC_MAPP 信息记录原则）。

# 2. 通用交付说明模板

除 QA 外，所有 Agent 的交付说明使用以下结构：

```markdown
# TASK-XXX 交付说明

**Task:** TASK-XXX
**Owner:** {Agent}
**日期:** YYYY-MM-DD
**依据:** {Task 依据 / 关联对象，一行}

## 结论
{一句话：验收标准是否全部满足；未满足项明确列出}

## 变更范围
- {模块 / 对象，每项一行；只写「改了什么、影响什么可验收行为」，不写实现细节}

## 验证证据
{表格：检查项 | 命令 | 结果；或逐条一行}

## 交付物清单
- {实际产物地址，链接到 workspace/ 或 deliverables/}

## 已知限制 / 待处理
- {无 / 逐项一行}

## 后续事项
- {无 / 具体动作，注明归属}

## 开发类附加
{仅 Frontend / Backend / Mobile；表格：Commit / Branch → Merge Target / Verification / 测试地址或构建产物}
```

### 字段要求

| 字段 | 要求 |
|---|---|
| 结论 | 必须明确「验收标准全部满足」或逐条列出未满足项；禁止「基本完成」「问题不大」等表述 |
| 变更范围 | 不超过 8 项；只写模块与可验收行为，不写字段名、阈值、配置项等实现细节 |
| 验证证据 | 不超过 10 项；必须包含实际命令、环境 / 版本、结果；不贴全量日志 |
| 交付物清单 | 只放实际地址，不写抽象类型；源代码不复制到 deliverables/ |
| 已知限制 | 影响验收判断的内容必须写全：环境问题、数据变更、历史影响、依赖行为 |
| 后续事项 | 只写有具体动作和归属的事项；无触发条件、无 Owner 的空话不写 |

# 3. 通用规则

## 3.1 限长

| 对象 | 上限 |
|---|---|
| 正文（不含表格与附件） | 1 页 A4 |
| 叙述性文字 | 300 字 |
| 变更范围 | 8 项 |
| 验证证据 | 10 项 |
| UI 截图 | 6 张 |
| QA 报告正文 | 2 页 A4（缺陷报告单独成文件，不受此限） |

## 3.2 禁止项

- 不写工作日志、讨论过程、已完成历史。
- 不复制源代码、全量日志、无关截图到交付物。
- 不重复粘贴 `workspace/` 已有资产的完整内容，只给指针。
- 不记录 Git 已保存的实现细节（字段名、阈值、配置项、逐文件解释等）。
- 不把产品内容（日报全文、页面文案全量、设计全稿）写入交付说明。
- 不用「适当」「完整」「尽快」等不可检查表述。
- 不把推测写成结论；根因未确认时标注「待分析」。
- 不用交付说明替代 `ACTIVE.md` 状态更新和通知 PM 的动作。

# 4. 各 Agent 差异

## 4.1 差异表

| Agent | 模板调整 | 必填附加字段 | 证据形式 | 详细资产位置 |
|---|---|---|---|---|
| Product | 「变更范围」改为「关键产品决策」（≤ 3 条）；「验证证据」改为「产品分析依据」 | 未决问题 | PRD 草案地址 + 决策摘要，不附技术方案 | `Agents/Product/workspace/` |
| UI | 无 | 页面结构与层级；关键交互与状态；组件与视觉规则；响应式适配；实现注意事项 | 设计稿链接 + 关键状态截图（每状态 1 张，≤ 6 张） | `Agents/UI/workspace/` |
| Frontend | 开发类附加 | 测试地址与启动方式、测试账号（任务涉及时） | 构建与浏览器检查结果摘要，不复制源代码 | `Agents/Frontend/workspace/` |
| Backend | 开发类附加 | API 变更摘要（路径 / 方法 / 关键变化）；数据变更摘要（迁移 / 回滚）；接口文档链接 | 接口与迁移验证摘要，完整 API 文档放 workspace 附链接 | `Agents/Backend/workspace/` |
| Mobile | 开发类附加 | 构建产物地址；验证设备与系统版本 | 构建产物 + 设备验证记录 | `Agents/Mobile/workspace/` |
| QA | 使用 4.2 专用模板 | 见 4.2 | 测试报告 + 缺陷报告 | `Agents/QA/deliverables/` |

## 4.2 QA 专用模板

```markdown
# TASK-XXX QA 报告

**Task:** TASK-XXX
**Owner:** QA Agent
**日期:** YYYY-MM-DD
**依据:** {PRD / Feature / Task 引用}

## 结论
{PASS / FAIL / BLOCKED，必须三选一}

## 验证范围
- {验证了什么}
- 排除范围：{明确不验证什么}

## 环境与版本
- {环境、版本 / Commit、账号、数据、执行时间}

## 执行记录
{表格：用例 / 操作路径 | 结果 | 证据}

## 缺陷摘要
- {编号 | 严重等级 | 一句话描述 | 状态 | 建议 Owner}

## 残余风险
- {逐项一行}

## 后续动作
- {建议动作与归属}
```

缺陷报告要求：每个需要处理的问题单独成文件，固定字段为标题、前置条件、环境与版本 / Commit、复现步骤、实际 vs 预期、影响范围、严重等级（Blocker / Critical / Major / Minor / Trivial）、证据、当前状态与建议 Owner。根因只有证据充分才能填写，否则写「待开发 Agent 分析」。

结论规则：`PASS` 只表示 QA 验证范围内通过；`FAIL` 不代表 QA 负责修复；`BLOCKED` 必须写明阻塞原因、已完成检查、未完成范围与需要谁处理。

# 5. PM 验收核对清单（30 秒）

```text
[ ] 结论一句话可读，明确覆盖 / 未覆盖验收标准
[ ] 变更范围与 Task 一致，无越权、无范围扩大
[ ] 验证证据可复核：有实际命令、环境与结果
[ ] 开发类 Task 含 Commit / Branch / Merge Target / Verification
[ ] QA Required: Yes 时含 QA PASS；无则不得验收
[ ] 已知限制明确，无悬空「待处理」
[ ] 未超限、未含禁止项——违反即打回，PM 不代改
```

# 6. 与其他文档的关系

| 文档 | 关系 |
|---|---|
| `specs/Task_Specification.md` | 本文件是其 Deliverable 字段的执行细则 |
| `workflows/Agent_Workflow.md` | 第 7 节提交审核时按本文件生成交付说明 |
| `contracts/{Agent}.md` | 各 Agent「交付补充」改为指向本文件，不重复定义 |
| `specs/Product_Requirement_Specification.md` | PRD 独立遵循该规格，本文件只规范交付说明本身 |
